QA_FINDING:
  AREA: Cross-track shared state — _logsLastSeen 500ms echo-suppression window
  FILE: vdsen-cliente.html
  LINE: ~1726
  SEVERITY: medium
  REPRO:
    1. Client completes a set → saveSet() fires updateDoc/setDoc to logs/{uid}
       with updatedAt = T (ms timestamp).  _logsLastSeen is set to T.
    2. Within 500ms, coach uses "📅 Cambiar semana actual" (setClientWeekManual) to
       advance the client to week 2, writing updatedAt = T+300 to logs/{uid}.
    3. Client snapshot fires with ts = T+300.
    4. Guard: `_logsLastSeen && ts <= _logsLastSeen + 500` → T+300 <= T+500 → TRUE → return.
    5. Coach's week advance is silently swallowed. Client stays at old week.
    6. Client has no indication the coach changed their week; continues at wrong week
       until page reload.
  EXPECTED: External writes (from a different originator) should bypass the echo guard,
            OR the guard window should be tightened to ≤ 50ms (only own echo).
  ACTUAL: Coach week-change within 500ms of any client save is silently ignored.
  NOTE: The coach's write uses `updatedAt: new Date().toISOString()` (ISO string) while
        the client uses `updatedAt: Date.now()` (numeric ms). The guard compares numeric
        ts to numeric _logsLastSeen. The ISO string coerces to NaN → ts = NaN →
        `NaN <= _logsLastSeen + 500` → FALSE → guard does NOT fire for ISO string writes.
        This means setClientWeekManual (ISO string) is NOT affected by this bug.
        But resetClientWeek uses `updatedAt: Date.now()` (numeric) — it IS affected.
  REFINED_REPRO: resetClientWeek uses Date.now() → echo guard fires within 500ms of client save.
  SUGGESTED_OWNER: SHARED

   `updatedAt: new Date().toISOString()` in the updateDoc payload. Otherwise
   coaches using Módulo D adjustment in production will see plan changes that
   active clients silently miss. This is a one-line fix.

R2 [HIGH]: The client live-logs listener REAL_WEEK regression bug means that
   coach week-reset operations during active client sessions leave the client
   in an inconsistent state. Consider either:
   (a) Treating a decrease in currentWeek from Firestore as a reload trigger
       (like activePlanId change), OR
   (b) Adding a toast + location.reload() in the listener when newWeek < REAL_WEEK.

R3 [MEDIUM]: Add an in-flight guard to _applyAllModuloD (disable button, set
   _applyModuloDInFlight flag) — mirrors the _applyRecBtn guard pattern at line 3298.

R4 [LOW]: The _logsLastSeen 500ms echo-suppression window is wider than needed.
   Tightening to 50-100ms would reduce the risk of swallowing concurrent coach
   writes during active client sessions. (Note: ISO string vs numeric updatedAt
   already provides some natural separation between coach and client writes.)

R5 [INFO]: T107-H test scope is narrow — it tests button disabled state on error
   but not visual state on success. Since the modal removes itself, this is not
   a user-visible regression risk, but the test intent should be documented.
