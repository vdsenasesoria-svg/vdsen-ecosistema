GAPS FOUND (4 total)
─────────────────────────────────────────────────────────────────────

R6-GAP-01 (SEVERITY: LOW)
  Function: submitPostSession (vdsen-cliente.html)
  Issue: The call to `await _confirmSessionDone(di)` is not wrapped in a try/catch.
  Current safety: _confirmSessionDone never throws (its own write is guarded by
  _doSaveLogs which absorbs all exceptions). This is a fragile contract — a future
  refactor of _confirmSessionDone could expose an unhandled rejection.
  Risk: Low in current code, medium in future.

R6-GAP-02 (SEVERITY: MEDIUM)
  Function: submitPostSession (vdsen-cliente.html)
  Issue: `showSessionSummary(di)` is called unconditionally after
  `await _confirmSessionDone(di)`. If the save failed, _confirmSessionDone shows an
  error toast ("⚠ NO SE GUARDÓ") AND then submitPostSession proceeds to call
  showSessionSummary — showing a "session complete" summary modal even though the
  session was not persisted. The user sees conflicting feedback: error toast followed
  by success summary.
  Risk: Medium UX confusion. User may believe the session was saved when it was not.
  Fix: Check a return value from _confirmSessionDone (or have it set a flag) before
  calling showSessionSummary.

R6-GAP-03 (SEVERITY: LOW)
  Function: submitPostSession (vdsen-cliente.html)
  Issue: The in-flight guard `_postSessionSubmitting` is reset to false by
  closePostSessionModal() which is called BEFORE `await _confirmSessionDone(di)`.
  There is no finally block to reset it on unexpected exception.
  Risk: Low in current code (because _confirmSessionDone never throws). Theoretical
  stuck-guard if an exception were ever introduced in the submit path.

R6-GAP-04 (SEVERITY: MEDIUM)
  Function: _applyTemplateToClient (vdsen-coach.html)
  Issue: This helper (called by openPlanTemplateLibrary) performs two Firestore writes:
  `await addDoc(collection(db, 'plans'), ...)` and
  `await updateDoc(doc(db, 'clients', clientId), { activePlanId: planRef.id })`.
  Neither is wrapped in try/catch, there is no finally block, and there is no user-
  visible error message on failure. A Firestore write failure silently aborts the
  template application with no feedback to the coach and no state restoration.
  Risk: Medium — silent data loss / silent activation failure.
  Fix: Wrap the writes in try/catch with a showToast on error.
